# Каталог интерфейса на новый язык

Два шага. Первый отправляет `languages/east-property.pot` переводчику, второй
собирает `.po` из ответа и карты переопределений. Оба повторяемы: перевод
кэшируется в опции `ep_deepl_cache`, так что второй прогон почти бесплатен.

```bash
cd ~/Projects/eastproperty.com/app/public/wp-content/themes/east-property
OUT=/tmp/i18n-ar && mkdir -p "$OUT"
cp scripts/i18n/overrides.ar.json "$OUT/overrides.json"

EP_OUT="$OUT" EP_LANG=ar wp eval-file scripts/i18n/translate-pot.php
EP_OUT="$OUT" EP_LOCALE=ar \
  EP_PLURAL="nplurals=6; plural=(n==0 ? 0 : n==1 ? 1 : n==2 ? 2 : n%100>=3 && n%100<=10 ? 3 : n%100>=11 ? 4 : 5);" \
  wp eval-file scripts/i18n/build-po.php

bash scripts/make-translations.sh
```

## Кто переводит

Провайдера задаёт `TRANSLATE_PROVIDER` в `.env` — gemini по умолчанию, deepl
запасной. **Перед командой его не подставить:** `core_env()` читает только
`$_ENV`, а `variables_order` здесь `GPCS`, без `E`, так что переменная из
шелла туда не доходит и подмена молча не происходит. Менять — в `.env`.

Переменные с префиксом `EP_` эти скрипты читают сами через `getenv()`, и вот
они из шелла работают. Отсюда вся путаница: в одном и том же вызове `EP_LANG`
действует, а `TRANSLATE_PROVIDER` нет.

| | |
|---|---|
| `EP_LANG` | слаг Polylang: `ar`, `hi`, `zh`. Провайдер сам знает, как он называет этот язык |
| `EP_OUT` | каталог для `raw.json`, `hints.json` и `overrides.json` |
| `EP_TARGET` | **только DeepL** — код языка в его собственной записи (`ZH-HANS`, `PT-PT`). С Gemini скрипт потребует `EP_LANG` |
| `EP_SOURCE`, `EP_MODEL`, `EP_CONTEXT` | **только DeepL**, остальные их не получают. По умолчанию `EN` и `quality_optimized` |

## Чем правим ответ

Две разные вещи, и путать их дорого.

`hints.json` — **подсказка на входе**: msgid подменяется однозначным
английским, а перевод всё равно приходит из API. Так чинилась неоднозначность
самого каталога: `Bed` в объявлении значит спальню, `Distress` — категорию
срочной продажи, и DeepL об этом знать неоткуда.

`overrides.json` — **замена на выходе**, по целому msgid. Здесь два рода
записей: имя бренда, которое переводить нельзя, и правки носителя языка,
которые обязаны пережить пересборку. Ключ с контекстом пишется как
`context\u0004msgid`, ключи с `_` в начале ни с чем не совпадают и служат
разделителями.

Правку из ревью мало внести в `.po` — следующий прогон `translate-pot.php`
затрёт её ответом API. Поэтому она идёт в `overrides.json`, и только потом
в каталог.

Подсказка, не совпавшая ни с одной строкой `.pot`, молча ничего не делает.
Проверять так:

```bash
wp eval 'require_once ABSPATH."wp-includes/pomo/po.php";
$h=json_decode(file_get_contents("/tmp/i18n-ar/hints.json"),true);
$po=new PO(); $po->import_from_file(get_stylesheet_directory()."/languages/east-property.pot");
$seen=array(); foreach($po->entries as $e){ $l=($e->context?$e->context."\x04":"").$e->singular;
 if(isset($h[$l]))$seen[$l]=1; elseif(isset($h[$e->singular]))$seen[$e->singular]=1; }
foreach($h as $k=>$v){ if($k[0]!=="_" && empty($seen[$k])) echo "мимо каталога: $k\n"; }'
```

### Подсказки нужны DeepL, а не Gemini

У модели отраслевые значения уходят в системный промпт из
`core/includes/tools/translation-domain.md`, и подсказка решает задачу,
которая уже решена. Замер 27.10.2026: те 16 строк, ради которых заводился
`hints.ar.json`, отданы Gemini **без подсказок** — смысл верен во всех
шестнадцати, ни эмоции вместо категории, ни школьной ступени, ни деревенского
дома. Расходится формулировка, и местами в пользу модели:

| msgid | DeepL + подсказка | Gemini без неё |
|---|---|---|
| `Townhouse` | منزل متلاصق | تاون هاوس |
| `Off Plan Properties` | العقارات المباعة على المخطط | عقارات على الخارطة |
| `Parent Property:` | العنصر العقاري الأصلي: | العقار الرئيسي: |
| `Latitude` | خط العرض الجغرافي | خط العرض |

Обратные случаи тоже есть: в `DLD Transfer` модель дописала `رسوم`
(«сборы»), которого в источнике нет, а `Handover` отдала как «передача
объекта» там, где ярлыку хватило бы «передачи». Так что файл подсказок не
выбрасываем — но при сборке через Gemini его стоит сначала не подключать и
посмотреть, что выйдет без него.

### Чего нет у DeepL

* **Глоссарий.** Пары `en→ar` API поддерживает, но тарифный лимит на число
  глоссариев занят существующим `EastProperty EN-DE`, и второй не создаётся —
  `Too many glossaries`.
* **Защита бренда в запросе.** `tag_handling=xml` с `ignore_tags` на
  `quality_optimized` отвечает `400`, а с `tag_handling=html` метки не
  соблюдаются: `<x>East Property</x>` всё равно приходит транслитерацией.
  Поэтому имя бренда возвращается латиницей через `overrides.json`.

Своя карта переопределений нужна каждому языку: ошибки у них разные. У хинди
это `Properties → गुणधर्म` (свойства-атрибуты), `Secondary → माध्यमिक`
(школьная ступень), `Studio → अध्ययन` (учёба), `Villa → गाँव` (деревня),
`Unit → इकाई` (единица измерения), `Parent X: → माता-पिता` (буквально
«мать-отец»), `Save → बचाएँ` («спасать»).

## Множественное число

Формы задаёт `EP_PLURAL`, и скрипт заполняет ровно столько форм, сколько
объявлено в `nplurals`. Китайский — одна форма (`nplurals=1; plural=0;`),
хинди — две (`nplurals=2; plural=(n != 1);`), вторая берётся из перевода
`msgid_plural`.

```bash
EP_OUT="$OUT" EP_LANG=hi wp eval-file scripts/i18n/translate-pot.php
EP_OUT="$OUT" EP_LOCALE=hi_IN EP_PLURAL="nplurals=2; plural=(n != 1);" \
  wp eval-file scripts/i18n/build-po.php
```

У арабского шесть форм, и единственное лежит **не в нулевом слоте**: нулевой
занят формой для нуля. `build-po.php` вычисляет нужный слот сам, прогоняя
формулу через `Plural_Forms` из ядра. Текстов при этом всего два — перевод
`msgid` и перевод `msgid_plural`, — так что падежи арабского счёта (2, 3–10,
11+) каталог не различает; где это важно, строку надо править руками.

Запускать `build-po.php` только с переменными окружения в том же вызове: без
`EP_LOCALE` он молча берёт `zh_CN`, а без `EP_OUT` не находит `raw.json` и
перезаписывает чужой каталог пустыми строками.

Имя файлов у арабского `*.ar.json`, а не `*.json`, потому что последние
заняты китайским.

## В каком состоянии каталоги

Все четыре — `ar`, `de_DE`, `hi_IN`, `zh_CN` — собраны **DeepL** и носителем
языка не вычитаны. Плейсхолдеры, теги, формы множественного числа и
отраслевые термины сверены, грамматика нет.

`de_DE`, `hi_IN` и `zh_CN` вдобавок собирались на старой модели с
автоопределением языка: без `source_lang` односложная метка опознавалась как
угодно (`Bed` вернулся как «мир», `Studio` как «исследование»), а сама модель
теряла плейсхолдеры. Их стоит пересобрать — это ~17 тыс. символов на язык.

`ar` собран уже с `source_lang=EN` и `quality_optimized`, на 35 подсказках.
Ответ модели не детерминирован: одна и та же строка в разных прогонах может
прийти с определённым артиклем и без, так что дословного совпадения двух
прогонов ждать не надо.
